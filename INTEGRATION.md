# Integration: one command, whole pipeline (Pranahv)

`master_pipeline.py` chains every student's module. Each stage keeps its own CLI; the master
only calls them in order, checks inputs, and records everything in `runs/<run>/manifest.json`.

```
broadcast clip ──► 1 motion (S1) ──► 2 densepose (S1) ──► 3 generate (S2) ──► 4 colour (S3)
                                                                                   │
            7 evaluate (S3 checks + PCK) ◄── 6 demo (source | final) ◄── 5 retime to 24 fps
```

| stage | module | output |
|---|---|---|
| motion | `pipeline_cli.py` | `data/processed_clips/<clip>/source_512.mp4, pose_data.json, metadata.json, control_pose.mp4` |
| densepose | `densepose/run_densepose.sh` (detectron2) + `patch_weak_frames.py` | `control_densepose_real.mp4, densepose_real_parts.npz, densepose_real_iuv.npz` |
| generate | `generate_cli.py` / `generation_engine.py` | `runs/<run>/generated.mp4` + `generated.mp4.json` (frame mapping, VRAM, prompts) |
| colour | `student3_v3` (default) or `student3_improved` (`--colour-engine v2`) | `runs/<run>/coloured.mp4`, plus `student3_v3/` era styles, mask overlay, side by side |
| retime | ffmpeg | `runs/<run>/final_24fps.mp4` (real-time speed) |
| demo | ffmpeg | `runs/<run>/demo_side_by_side.mp4` |
| evaluate | `student3_improved/evaluate.py` + `integration/eval_pck.py` | `runs/<run>/evaluation.json` |

Stages whose outputs exist are skipped, so a failed run resumes. `--force <stage>` redoes one,
`--only <stage>` runs one, `--skip <stage>` leaves one out, `--dry-run` prints the plan.

## Run

```bash
# both clips are already processed (motion + DensePose in the repo):
python master_pipeline.py --clip-id good_cover_drive_final --image data/historical_images/bradman.jpg --role batsman
python master_pipeline.py --clip-id bowler_delivery_001 --image data/historical_images/modern_bowler.jpeg --role bowler

# with SAM2 for colour:
python master_pipeline.py --clip-id bowler_delivery_001 --image data/historical_images/modern_bowler.jpeg \
    --sam2-config configs/sam2.1/sam2.1_hiera_t.yaml --sam2-checkpoint models/sam2.1_hiera_tiny.pt

# a new raw clip (runs motion and DensePose too; DensePose needs WSL/Linux + detectron2):
python master_pipeline.py --reference-video data/raw/pull_shot.mp4 --clip-id pull_001 --action-type pull_shot \
    --image data/historical_images/bradman.jpg --role batsman --track-id 1 --crop-margin 0.45 \
    --densepose-python ~/dp/bin/python
```

`--generated <video>` skips generation and uses a video Student 2 already made (no GPU needed); the
frame mapping then comes from Student 3 v3's detected holds, and held frames are dropped before retiming.
`--force all` redoes generation onwards (motion and DensePose only when `--reference-video` is given).
See `RUN_ON_GPU.md` for the laptop setup and `COLAB.md` for running on Colab.

`--python` picks the interpreter for generation/colour if the diffusers env is separate.

Exit codes (same as Student 1's CLI): 0 ok, 2 arguments, 3 missing dependency, 4 bad input,
5 model/inference failure, 6 output/ffmpeg failure, 70 unexpected.

## Contracts between stages

* **Student 1 → 2**: 512x512, 24 fps, `frame_index` t is the same frame in every file of a clip.
  `densepose_real_parts.npz` holds exact part ids (0 background, 1..24); the mp4 is the same ids in PARULA colours.
* **Student 2 → 3/eval**: `generated.mp4.json` records which source frame every output frame came from
  (`output_frame_to_source_frame`), the crop that maps 512 DensePose pixels to the 384x512 output
  (`sampling.crop_in_padded_px`, `pad_px`), prompts, seed, VRAM and broken frames that were replaced.
* **Student 3 v3 (default)**: gets the generation sidecar (`--sidecar`) and the exact part ids
  (`--parts-npz`), so its masks use the real frame mapping and crop even when generation used a
  custom `--window`, and no colour decoding is needed (mask coverage 0.885 → 0.907 bowler,
  0.945 → 0.964 batsman on the test runs). Era outputs (1930s newsreel, remaster, 1970s broadcast)
  land in `runs/<run>/student3_v3/`.
* **Student 3 v2** (`--colour-engine v2`): SAM2 prompt boxes are computed from the real DensePose
  parts of the first generated frame (`integration/student3_prompts.py`); config saved as
  `runs/<run>/student3_config.json`.

## Timing

The engine generates 16 keyframes (the motion adapter's window). Milestone 3 exported them at 7 fps
with 3 + 7 frozen frames; the master exports no frozen frames, plays the keyframes at their real-time
rate (24 fps / keyframe spacing: about 5.1 fps batting, 3.2 fps bowling) and motion-interpolates to
24 fps with ffmpeg. Interpolated in-between frames are not generated by the model (stated in the manifest).
`--legacy-timing` reproduces the Milestone 3 timing.

Two speeds exist on purpose: `final_24fps.mp4` interpolates between keyframes (smooth, modern),
while Student 3 v3's era files retime by holding frames (`era_newsreel_1930s.mp4` at 18 fps with
uneven holds), which is how old film actually looked.

### `--auto-window`

The built-in windows spread 16 keyframes over the whole clip, so the bowler's arm action (frames
~89 to 120) gets about 5 keyframes. `--auto-window` finds the peak wrist speed in Student 1's pose
(ignoring low-confidence frames) and samples 2 s before to 0.45 s after it: bowler 63..120
(release at 111, 9 keyframes on the arm), batsman 39..98 (impact around 87). Opt-in, because it
changes what Student 2 generates.

## Motion fidelity (PCK)

`integration/eval_pck.py` runs Student 1's DWPose on the generated keyframes, maps the reference
joints through the recorded crop, and reports PCK@0.05/0.1/0.2 (threshold = alpha x max side of the
reference body box; joints DWPose misses count as wrong) plus the cosine similarity of joint motion
between keyframes. Body joints only. Needs `easy-dwpose` in the env that runs the master.
When v3 coloured the run, Krishav's PCK (torso-normalised, plus the bowling arm on its own) is
computed from the same DWPose output and stored next to it in `evaluation.json`.

## Bowler proxy (no GPU)

`python -m student3_v3.make_proxy` builds a stand-in for the generated bowler from the real
footage (Krishav's tool). It is only for checking Student 3; never present it as generated.
`data/student3/bowler_delivery_001_proxy/` holds that run.

## Known limits (not fixed here)

* The batsman's bat is drawn by the engine at fixed angles (96° to 162°), not tracked from the source.
* Compositing uses the DensePose silhouette as the matte. Where the generated body is thinner than
  the silhouette, the generated background shows as a bright halo; Student 3 keeps luminance, so the
  halo survives colouring. Needs a matte refinement in `generation_engine.py`, tested on GPU.
* The bowler reference crop default only fits `modern_bowler.jpeg` (`--ref-box` for other photos).
* `data/generated_clips/test_run/m3_vram_report.json` describes an older run (139 frames, 512x512);
  new runs write `runs/<run>/vram_report.json`.
